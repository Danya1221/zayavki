# zayavki — оформление заказов и мини-CRM в Telegram

Обычный Telegram-бот для клиентов и администраторов. Работает в паре с
[rozniysa](https://github.com/Danya1221/rozniysa): нажатие на товар в прайсе
открывает оформление именно этого варианта. Mini App и онлайн-оплата не используются.

## Что реализовано

- Корзина: до 30 разных товаров, количество до 20 на позицию, индивидуальные и общие примечания.
- Получатель, российский телефон, способ получения, город, улица, дом, квартира/офис,
  примечания к каждому этапу. Телефон приводится к `+7`; формат адреса проверяется.
  Наличие адреса в справочнике и владение номером через SMS не проверяются.
- Курьер / транспортная компания; самовывоз появляется после настройки адреса.
- Платная доставка: менеджер указывает сумму, покупатель подтверждает итог.
  Изменение суммы требует нового подтверждения. Самовывоз — без доставки.
- Клиент видит только свои заявки. Администраторы из `ADMIN_IDS` видят товары, варианты,
  количество, цену, контакты, Telegram ID/username, адрес, примечания и историю статусов.
  Username может отсутствовать — сохраняется ID и ссылка на профиль.
- Статусы: новая, в работе, сборка, у курьера, готов к выдаче, завершено, отменено,
  возврат, брак. Администратор может добавить, переименовать, упорядочить статусы
  и указать, какой завершает заявку. Внутренние заметки скрыты от покупателей.
- Завершённые и отменённые заявки сразу уходят из активного списка в архив.
  Через **7 суток после завершения** удаляются из базы при ближайшей очистке.
  Открытый заново возврат/брак остаётся активным до следующего завершения.
- Приветствие сохраняется. Незавершённая корзина сбрасывается при изменении цены/
  доступности любой её позиции или после 24 часов бездействия. Отправленная заявка
  хранит снимок цены и состава: новые прайсы его не переписывают.
- Ночью и при сбое поставщика заявку можно отправить; администратор видит необходимость
  подтвердить цену и наличие. Заявка не означает резерв у поставщика.
- Транзакции, защита от повторной отправки, очередь уведомлений, одна активная копия процесса.

## Запуск двух сервисов

1. Создай **два разных** бота в BotFather: витрина/управление (`rozniysa`) и оформление
   (`zayavki`). Нужны новые действующие токены. Старые значения со скриншотов не включены в код.
2. Создай PostgreSQL и подключи оба сервиса к одной базе через **одинаковый**
   `RETAIL_DATABASE_URL`. База должна быть доступна обоим процессам.
3. Разверни этот репозиторий отдельным сервисом: Dockerfile и `railway.toml` уже готовы.
   Команда — `python -u main.py`. Одна реплика, без публичного HTTP-домена и webhook.
4. Заполни Variables из `.env.example`. Обязательны `BOT_TOKEN`, `ADMIN_IDS`,
   `RETAIL_DATABASE_URL`. Не добавляй секреты в GitHub.
5. Укажи сведения продавца (`SELLER_INFO`), HTTPS-ссылки на политику данных
   (`PRIVACY_URL`) и условия покупки (`TERMS_URL`). Без них бот отвечает, но оформление
   ещё не открывается. Покупатель знакомится с ними до ввода контактов;
   время и ссылки сохраняются в снимке заявки.
6. Каждый администратор должен открыть бота и нажать `/start`, чтобы Telegram разрешил
   ему получать уведомления. `/admin` открывает управление.
7. В `rozniysa` укажи username **этого** бота в `ORDER_BOT_USERNAME`, подключи поставщиков
   и опубликуй прайс. Ссылка на каталог попадёт в общую базу автоматически;
   при необходимости `CATALOG_URL` задаёт свою ссылку.
8. Проведи контрольный заказ с отдельного клиентского аккаунта: два товара, примечание,
   адрес, цена доставки, подтверждение, смена статуса и архив.

При первом переходе по ссылке Telegram может показать кнопку **«Начать»** — это часть
[механизма deep links](https://core.telegram.org/bots/features#deep-linking).
В ссылке передаётся только идентификатор товара; цену бот читает из общей базы.

## Переменные

| Переменная | Назначение |
| --- | --- |
| `BOT_TOKEN` | Токен бота оформления |
| `ADMIN_IDS` | Числовые ID администраторов через запятую |
| `RETAIL_DATABASE_URL` | Общая PostgreSQL-база двух ботов |
| `SHOP_NAME` | Название магазина в приветствии |
| `SELLER_INFO` | Реальные сведения продавца и способ связи |
| `PRIVACY_URL`, `TERMS_URL` | Опубликованные документы магазина по HTTPS |
| `PICKUP_ADDRESS` | Адрес самовывоза; пусто — кнопка скрыта |
| `CATALOG_URL` | Необязательная ссылка на прайс; иначе берётся из общей базы |
| `ARCHIVE_DAYS` | По умолчанию 7 |
| `DRAFT_HOURS` | Очистка черновиков, 1–24, по умолчанию 24 |
| `CATALOG_FRESH_SECONDS` | Срок свежести прайса, по умолчанию 1800 секунд |

Команды покупателя: `/start`, `/cart`, `/cancel`. Статусы, архив, поиск, заметки,
сумма доставки и приветствие доступны кнопками в `/admin`.

## Очистка и ограничения

Telegram обычно разрешает [удалять сообщения моложе 48 часов](https://core.telegram.org/bots/api#deletemessage).
Если старую карточку удалить нельзя, бот заменяет её текст нейтральным и убирает кнопки.
Приветствие сохраняется. Входящие контакты и адреса удаляются из переписки сразу после
обработки. Очистка выполняется, пока сервис работает; после простоя продолжится при запуске.
При отсутствии доступа к Telegram очистка сообщений может завершиться позже очистки базы.
Пересланные сообщения, пользовательские копии и резервные копии хостинга бот не контролирует.
Срок резервных копий базы настрой отдельно в соответствии с принятым сроком хранения.

Если Telegram не подтвердил отправку уведомления, повторная отправка автоматически
не выполняется, чтобы не создавать дубли. Сама заявка остаётся в `/admin` → «Активные».
При блокировке бота клиентом/администратором уведомление не доставляется; база сохраняется.

Архив на 7 дней — правило хранения в этой системе. Срок гарантии и условия возврата
задаются документами магазина. Код не отклоняет обращение автоматически из-за прошедших
семи дней. Формат `+7` и поля адреса сами по себе не означают полного соответствия
законодательству: нужны реальные документы продавца и подходящее размещение данных.

## Локальная разработка и проверка

Python 3.12. Для локальной пары можно использовать один абсолютный путь SQLite:
`RETAIL_DATABASE_URL=sqlite:////absolute/path/retail.db` в обоих сервисах.
Для двух раздельных контейнеров/хостов используй PostgreSQL.

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Заполни .env перед запуском
python main.py
```

```bash
python -m compileall -q .
python -m unittest discover -s tests -v
# Дополнительно на ОТДЕЛЬНОЙ тестовой PostgreSQL-базе:
TEST_DATABASE_URL=postgresql://... python -m unittest discover -s tests -v
```

**Тесты очищают таблицу `retail_data` в `TEST_DATABASE_URL`: никогда не указывай рабочую базу.**
GitHub Actions проверяет SQLite и отдельный PostgreSQL 16. Интеграционный сценарий пары
находится в `rozniysa/tests/integration_pair.py`.

`retail_store.py` — одинаковый версионированный контракт двух проектов. При его изменении
обновляй оба репозитория и запускай интеграционный тест. Не запускай разные checkout-боты
с одной рабочей базой магазина: таблицы предназначены для одной пары ботов.
